# 구현 가이드

기본 모션 매칭을 유니티에서 직접 구현하기 위한 단계별 안내입니다. 각 단계는 앞 단계의 결과 위에서만 확인할 수 있도록 순서를 잡았습니다. 단계마다 **완료 기준**을 눈으로 확인한 뒤 다음으로 넘어가세요.

코드 조각은 [PORTING.md](PORTING.md)에, 출처는 [REFERENCES.md](REFERENCES.md)에 있습니다.

## 전체 구조

```
[오프라인 / 에디터]
  애니메이션 클립 ──► 포즈 DB (본별 위치·회전·속도·각속도, 접촉, 클립 범위)
                  ──► 특징 DB (프레임당 27차원, 정규화) + AABB

[런타임 / 매 프레임]
  입력 ─► 목표 속도·회전 ─► 미래 궤적 예측 ─► 쿼리 벡터
                                                  │
                         (0.1초마다, 또는 입력 급변 시) 탐색
                                                  │
       더 나은 프레임이면 전환 + 관성 보간 오프셋 기록
                                                  │
  프레임 진행 ─► 포즈 조회 ─► 관성 보간 적용 ─► 시뮬레이션 갱신
       ─► 보정·클램핑 ─► 발 고정 IK ─► 본에 적용
```

런타임 순서는 원본 `controller.cpp`의 갱신 루프(1495~2093행)와 같습니다.

## 0단계: 준비

- **유니티 버전**: 6 이상 권장. JLPM22 패키지가 6에서만 시험되었으므로 대조할 때 편합니다.
- **패키지**: `Burst`, `Mathematics`, `Collections`. 8단계 전까지는 없어도 됩니다.
- **데이터**: [lafan1-resolved](https://github.com/orangeduck/lafan1-resolved)를 권합니다. FBX와 스킨 캐릭터(`Geno.fbx`)가 함께 있고 60fps라 재샘플링이 필요 없습니다. 유니티 임포트 결과(스케일, 리그)는 확인하지 못했으니 받아서 직접 확인하세요.
- **시작 클립**: 원본 데모와 같은 3개면 충분합니다. `walk1_subject5`, `run1_subject5`, 그리고 정지 자세용으로 `pushAndStumble1_subject5`의 짧은 구간.

**라이선스 주의**: LAFAN1과 lafan1-resolved는 비상업용이고 원본은 변경 금지(CC BY-NC-ND 4.0) 조건이 붙어 있습니다. 이 저장소가 공개라면 데이터 파일과 그것으로 구운 DB는 커밋하지 마세요. `.gitignore`에 `Assets/MocapData/`와 `Assets/StreamingAssets/`를 미리 넣어 두었습니다.

## 1단계: 포즈 DB 굽기 (에디터)

**목표**: 클립들을 프레임 단위 배열로 풀어 파일 하나로 저장한다.

저장할 것 (원본 `database.h`의 `struct database`와 동일):

| 배열 | 크기 | 내용 |
|---|---|---|
| `bonePositions` | 프레임 × 본 | 부모 기준 로컬 위치. 0번은 시뮬레이션 본(월드) |
| `boneRotations` | 프레임 × 본 | 부모 기준 로컬 회전 |
| `boneVelocities` | 프레임 × 본 | 로컬 위치의 시간 미분 |
| `boneAngularVelocities` | 프레임 × 본 | 로컬 회전의 각속도 (rad/s) |
| `boneParents` | 본 | 부모 인덱스. 루트는 -1. 부모가 항상 자식보다 앞 |
| `rangeStarts`, `rangeStops` | 클립 수 | 각 클립의 프레임 범위 |
| `contactStates` | 프레임 × 2 | 왼발·오른발 접촉 여부 |

절차:

1. **샘플링**: 에디터 스크립트에서 리그 인스턴스에 `clip.SampleAnimation(go, time)`을 1/60초 간격으로 호출하고 각 본의 `localPosition`, `localRotation`을 읽습니다. 리그는 Generic으로 임포트하는 쪽이 단순합니다. Humanoid 클립에서 이 호출이 기대대로 동작하는지는 확인하지 못했습니다.
2. **시뮬레이션 본 추가**: 0번 본으로 삽입합니다.
   - 위치: 골반(또는 상체 척추)을 바닥에 투영 (`y = 0`).
   - 회전: 골반의 전방 벡터를 바닥에 투영해 `Quaternion.LookRotation`.
   - 기존 루트(골반)는 시뮬레이션 본 기준 로컬 값으로 다시 계산합니다: `pos = inv(simRot) * (hipWorldPos - simPos)`, `rot = inv(simRot) * hipWorldRot`.
   - 골반의 "전방"이 어느 로컬 축인지는 리그마다 다릅니다. 원본 데이터는 로컬 +Y였습니다. T포즈에서 확인하세요.
3. **평활화 (나중에 해도 됨)**: 원본은 Savitzky-Golay 필터를 위치에 창 31, 방향에 창 61(3차)로 적용합니다. 골반의 좌우 흔들림이 궤적에 섞이는 것을 막기 위해서입니다. JLPM22는 이 단계를 생략하고도 동작하므로, 처음에는 생략하고 궤적이 떨리는 것이 보이면 추가하세요.
4. **속도**: 중앙 차분을 씁니다. `v[i] = (x[i+1] - x[i-1]) / (2 * dt)`. 각속도는 `MMath.AngularVelocity`를 앞뒤로 구해 평균합니다. 클립 경계를 넘어 차분하지 않도록 클립마다 따로 계산합니다.
5. **접촉**: 발끝 본의 월드 속도 크기가 0.15 m/s 미만이면 접촉. 이후 중앙값 필터(창 6)로 짧은 깜빡임을 제거합니다.
6. **쿼터니언 부호 정리**: 인접 프레임 간 내적이 음수면 부호를 뒤집습니다. 안 하면 각속도가 튑니다.

나중에 추가할 것: 좌우 미러링(데이터 2배), 10% 가속(원본은 모션캡처가 게임용으로는 느리다는 이유로 적용).

**완료 기준**: 구운 DB의 한 클립을 처음부터 끝까지 본에 그대로 적용해 재생했을 때 원본 클립과 눈으로 구분되지 않는다. 시뮬레이션 본 위치에 기즈모를 그리면 캐릭터 발밑을 부드럽게 따라간다.

## 2단계: DB 재생기

**목표**: 프레임 인덱스 하나로 캐릭터를 움직인다.

- `frameTime += 60 * Time.deltaTime; frame = (int)frameTime;` 방식으로 진행합니다. 원본은 60fps 고정을 가정하고 `frame_index++`를 쓰지만 유니티에서는 프레임률이 흔들립니다.
- 본 적용: Animator 없이 `Transform.localRotation`을 직접 쓰는 것이 가장 단순합니다. 위치는 골반(1번 본)만 적용하고 나머지는 회전만 씁니다.
- 루트: PORTING.md 5절의 `UpdateAnimationSpaceOrigin` / `ApplyRoot`를 구현합니다. 이 시점에는 클립 시작에서 한 번만 기준점을 잡습니다.
- 클립 끝에 닿으면 일단 멈추거나 처음으로 되돌립니다.

**완료 기준**: 임의의 프레임 번호로 점프했을 때 캐릭터가 **제자리에서** 그 포즈로 바뀌고(월드 위치가 튀지 않고), 이후 그 클립의 루트 모션대로 걸어간다.

## 3단계: 특징 DB

**목표**: 프레임마다 27차원 벡터를 만들고 정규화한다.

| 순서 | 특징 | 차원 | 가중치 |
|---|---|---|---|
| 0 | 왼발 위치 | 3 | 0.75 |
| 3 | 오른발 위치 | 3 | 0.75 |
| 6 | 왼발 속도 | 3 | 1.0 |
| 9 | 오른발 속도 | 3 | 1.0 |
| 12 | 골반 속도 | 3 | 1.0 |
| 15 | 궤적 위치 (20, 40, 60프레임 뒤의 XZ) | 6 | 1.0 |
| 21 | 궤적 방향 (20, 40, 60프레임 뒤의 XZ) | 6 | 1.5 |

- 모든 값은 **해당 프레임의 시뮬레이션 본 기준 로컬 좌표**입니다. 이래야 캐릭터가 월드 어디에 있든 어느 쪽을 보든 같은 동작이 같은 벡터가 됩니다.
- 발 위치·속도는 순기구학(FK)으로 캐릭터 공간 값을 구합니다. 속도 FK는 `v = 부모속도 + 부모회전 * 로컬속도 + cross(부모각속도, 부모회전 * 로컬위치)`입니다 (원본 `forward_kinematics_velocity`).
- 미래 프레임 인덱스는 **같은 클립 범위 안으로 클램프**합니다 (`database_trajectory_index_clamp`). 다음 클립으로 넘어가면 안 됩니다.
- 정규화는 특징 그룹 단위로 `NormalizeFeature`를 호출합니다 (PORTING.md 3절).

**완료 기준**:
- 정규화 후 각 차원의 평균이 0에 가깝다.
- 재생 중 현재 프레임의 특징을 역정규화해 기즈모로 그리면, 발 위치 점이 실제 발에 붙어 있고 궤적 점 3개가 캐릭터가 **실제로 곧 지나갈 자리**에 찍힌다.

두 번째 기준이 가장 중요합니다. 여기서 어긋나면 좌표 변환이 틀린 것이고, 이후 단계의 모든 문제가 여기서 나옵니다.

## 4단계: 시뮬레이션 오브젝트와 궤적 예측

**목표**: 입력만으로 움직이는 가상의 점을 만들고 그 미래를 예측한다. 이 단계에서는 캐릭터와 연결하지 않는다.

- 상태: `simPos`, `simVel`, `simAcc`, `simRot`, `simAngVel`.
- 목표 속도: 스틱 입력을 카메라 방위각으로 회전시키고 최고 속도를 곱합니다. 원본은 시뮬레이션의 로컬 방향에 따라 전진 4.0 / 측면 3.0 / 후진 2.5 m/s(달리기), 1.75 / 1.5 / 1.25(걷기)를 씁니다.
- 목표 회전: 스틱이 기울어져 있으면 이동 방향을 보도록, 놓으면 직전 값을 유지합니다.
- 갱신: `CharacterPositionUpdate`와 `SimpleSpringDamper`(회전). 반감기는 둘 다 0.27초에서 시작합니다.
- 예측: PORTING.md 6절.

**완료 기준**: 캡슐 하나가 스틱에 부드럽게 반응하며 움직이고, 앞쪽에 예측 점 3개가 그려진다. 스틱을 꺾으면 예측 점들이 곡선을 그리며 새 방향으로 휜다. 스틱을 놓으면 점들이 캡슐 쪽으로 모인다.

이 속도 값들은 **데이터와 맞아야** 합니다. 걷기 클립의 실제 루트 속도가 1.4 m/s인데 시뮬레이션이 1.75로 달리면 캐릭터가 영원히 따라잡지 못합니다. DB의 루트 속도 분포를 한 번 출력해 보고 맞추세요.

## 5단계: 탐색과 전환

**목표**: 3단계와 4단계를 연결한다. 관성 보간 없이 전환하므로 포즈가 튀는 것이 정상이다.

1. 쿼리 구성: 포즈 15차원은 현재 프레임에서 복사, 궤적 12차원은 예측값으로 채움.
2. 탐색 조건: 0.1초 타이머 만료, 또는 클립 끝 도달. 클립 끝이면 `bestIndex = -1`로 넘겨 반드시 다른 곳으로 가게 합니다.
3. 전수 탐색으로 구현 (PORTING.md 4절에서 박스 검사 제외).
4. `bestIndex != frame`이면 `frame = bestIndex`로 바꾸고 루트 기준점을 다시 잡습니다.

**완료 기준**: 스틱을 밀면 걷기·달리기 구간으로, 놓으면 정지 구간으로 넘어간다. 방향을 틀면 회전 동작이 나온다. 전환 순간 포즈가 튄다. 캐릭터가 시뮬레이션 캡슐과 대략 같은 방향으로 가지만 점점 벌어질 수 있다.

안 될 때 확인 순서:

1. 전환이 전혀 안 일어남 → 쿼리를 정규화했는지, `ignoreSurrounding`이 DB 크기보다 크지 않은지.
2. 엉뚱한 동작만 나옴 → 3단계 완료 기준을 다시 확인. 쿼리의 궤적 기즈모와 선택된 프레임의 궤적 기즈모를 겹쳐 그려 보세요.
3. 0.1초마다 계속 다른 곳으로 튐 → 현재 프레임 비용을 기준선으로 쓰고 있는지.

## 6단계: 관성 보간

**목표**: 전환 순간의 튐을 없앤다.

- 본마다 오프셋 4개를 유지합니다: 위치, 속도, 회전, 각속도.
- 전환 시: 모든 본에 `Inertializer.Transition(src = 직전 프레임 DB 값, dst = 새 프레임 DB 값)`.
- 매 프레임: `Inertializer.Update`로 DB 값에 오프셋을 더해 출력.
- 반감기 0.1초.
- 루트는 5단계 방식을 유지합니다 (PORTING.md 5절 "단순한 방법").

**완료 기준**: 전환이 눈에 띄지 않는다. 반감기를 1초로 올리면 전환이 느릿하게 풀리는 것이 보이고, 0으로 내리면 5단계처럼 튄다.

## 7단계: 보정과 클램핑

**목표**: 캐릭터가 시뮬레이션에서 벗어나지 않게 한다.

- 매 프레임 `AdjustPositionByVelocity`, `AdjustRotationByVelocity` 후 `ClampPosition`, `ClampRotation`.
- 결과는 루트 Transform에 직접 쓰지 말고 **기준점**(`worldOriginPos`, `worldOriginRot`)에 차이만큼 반영합니다.
- 캐릭터 속도·각속도는 직전 프레임 루트와의 차분으로 구합니다.

**완료 기준**: 장시간 조작해도 캐릭터가 캡슐에서 0.15m 넘게 벗어나지 않는다. 정지 상태에서 캐릭터가 미끄러지지 않는다. 보정을 끄면 서서히 벌어지는 것이 보인다.

튜닝 방향 (글의 요지):

- 반응이 굼뜨다 → 시뮬레이션 반감기를 줄이기 전에 데이터가 그 반응성을 갖고 있는지 확인. 없으면 시뮬레이션만 빨라지고 캐릭터가 끌려다닙니다.
- 발이 미끄러진다 → `maxRatio`를 낮추거나 클램프 거리를 넓힙니다.
- 제자리에서 빙글 돈다 → 회전 반응성이 너무 높습니다. 회전 반감기를 위치보다 길게 둡니다.

## 8단계: 탐색 가속

- AABB 2단 구조 추가. **전수 탐색과 결과가 같은지** 수백 번의 무작위 쿼리로 비교합니다.
- Burst `IJob`으로 이전.
- 입력 급변 시 강제 탐색: 목표 속도·회전의 변화율이 임계값(원본 50)을 넘었다가 내려오는 순간 타이머를 무시하고 탐색합니다.

**완료 기준**: 프로파일러에서 탐색 시간이 줄었고, 동작은 8단계 전과 같다.

## 디버깅용 시각화

O3DE 구현 글이 권하는 방법들입니다. 5단계 이후 문제가 생기면 유용합니다.

- **비용 그래프**: 선택된 프레임의 비용을 시간축으로 그립니다. 동작이 어색한 순간과 비용이 치솟는 순간이 겹치면 DB에 그 동작이 없다는 뜻입니다.
- **특징 분포 히스토그램**: 전진·후진·횡이동, 빠른 회전·느린 회전이 각각 얼마나 들어 있는지 봅니다.
- **선택 프레임 표시**: 현재 어느 클립의 몇 번째 프레임인지 화면에 띄웁니다. 같은 구간만 맴도는지 바로 보입니다.
